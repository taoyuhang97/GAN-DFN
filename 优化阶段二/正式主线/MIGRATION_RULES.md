# 代码迁移准入规则

## 1. 目的

本规则用于控制哪些代码可以从旧目录迁入 `优化阶段二/正式主线`。

原则很简单：

- 不是所有能跑的代码都要迁
- 只有“有效且必要”的代码才迁


## 2. 必须同时满足的三个条件

### 条件一：有效

至少满足以下检查中的大部分：

- 语法可通过
- 依赖关系清楚
- 输入输出明确
- 当前仓库环境下可执行或可静态验证
- 不依赖明显失效的旧路径和旧目录结构


### 条件二：必要

该脚本必须直接服务于正式主线某一步：

- 原始数据整理
- 层位框架
- 真实井属性提取
- 真实井裂缝预测
- 正式虚拟测井构造
- T4-T7 统一样本
- 裂缝密度体
- 初始 DFN
- DFN 井控校正

如果只是：

- 历史对比
- 报表美化
- 中间调试
- 一次性验证

则不迁入正式主线。


### 条件三：口径一致

脚本逻辑必须与当前项目正式口径一致：

- 使用正式 `01/02/03`
- 只认 `T4-T7`
- `Density` 是主监督
- `HasFracture` 主要留给最终 DFN 校正
- demo 先做 `3000m x 3000m`
- 密度体必须是属性驱动预测，不是空间平滑扩散

凡是与这些口径冲突的脚本，即使能跑，也不迁。


## 3. 迁移前检查动作

每次迁移前至少做以下动作：

1. 阅读脚本
2. 判断它服务于哪一步
3. 检查是否包含旧方法逻辑
4. 做最小语法检查
5. 若有必要，做最小运行验证
6. 形成“迁 / 不迁 / 重写后再迁”结论


## 4. 迁移后的要求

迁入正式主线后的脚本应满足：

- 路径配置清楚
- 文件职责单一
- 输出字段明确
- 不再引用调试目录
- 能被后续正式脚本直接调用


## 5. 当前默认策略

- `当前任务` 目录：视为调试和中间实现区
- `虚拟测井构造` 目录：视为旧链路和可复用来源区
- `正式主线` 目录：视为最终保留代码区
