# 研究内容一 代码继承清单

## 1. 结论先行

`优化阶段二/研究内容一` 可以继承的主要是：

- 目录拆分思路
- 输入输出整理方式
- 少量通用 I/O 工具
- 交付物打包骨架

不能直接继承为当前正式方法的主要是：

- 虚拟测井井周属性构造逻辑
- 虚拟测井弱标签外推逻辑
- 基于该弱标签直接形成正式训练样本的逻辑
- 名义上的 `DFN 井轨迹校正包` 构造逻辑

原因很直接：

- 它的“虚拟井”属性没有从虚拟井位置真实读取
- 它的“虚拟井”密度标签本质是源井密度按距离衰减复制
- 它形成的是工程原型，不是当前项目要求的正式监督样本

## 4. 推荐修改方案

### 4.1 总体原则

研究内容一不要继续作为“正式方法链路”运行。

应改为两类用途：

- `工程参考层`
- `交付打包层`

真正参与当前阶段二正式任务的，只保留以下两类能力：

- 通用读写和打包
- 字段模板和交付目录模板


### 4.2 应如何修改

#### 修改一：停用旧的 1-6 步旧方法链

处理方式：

- 保留代码，但标记为 `legacy_prototype`
- 不再作为当前正式入口调用

结果：

- 避免旧逻辑继续污染当前正式结果


#### 修改二：把“交付三样结果”的打包逻辑迁入当前任务

处理方式：

- 以 `package_three_outputs.py` 为骨架
- 新建当前任务版正式打包脚本

新输入改为：

- `01`: 正式真实测井结果目录
- `02`: 正式虚拟测井结果目录
- `03`: 正式 DFN 井轨迹校正包目录

结果：

- 最终交付仍然保持清晰三段式
- 但来源全部切换到当前正式链路


#### 修改三：把字段统一模板吸收到当前样本构造脚本

处理方式：

- 将 `SourceWellName / TrackWellName / X / Y / TIME / Density / HasFracture / 属性列 / 层位列` 的输出模板
- 统一并入当前 [build_density_training_samples.py](/home/tyh/projects/petroleum/code/GAN-DFN/优化阶段二/当前任务/step2_target_block_and_density_samples/build_density_training_samples.py)

结果：

- 当前正式样本包字段会更稳定
- 不需要再依赖研究内容一的旧汇总脚本


#### 修改四：如需“虚拟井索引表”，改成真实道索引口径

处理方式：

- 保留“按井周生成候选轨迹”的概念
- 但必须基于当前 demo 区块内真实存在的 `TraceIdx/X/Y/IX/IY`
- 只作为候选索引，不作为外推标签生成器

结果：

- 后续若做解释图、井周对比、局部 DFN 控制，会有标准候选轨迹表可用


## 5. 修改后的结果会是什么样

修改完成后，研究内容一不再承担“生成正式训练样本”的角色。

它会退化成一个辅助层，输出价值主要变成：

- 一套可复用的交付打包脚本
- 一套统一字段模板
- 一套候选轨迹索引辅助表
- 一些数据检查脚本

而当前正式结果将全部由 `当前任务` 链路产出：

- `step1_unified_samples`: 统一点样本表
- `step2_t4_t7_density_package`: T4-T7 正式密度样本总包
- `step2_target_block_and_density_samples`: demo 区块正式训练样本包
- `step3_candidate_a_density_volume`: demo 区块正式预测密度体


## 6. 和后续流程能否流畅对接

可以，而且会比现在更顺。

原因有三点：

### 1) 上游口径统一

当前正式链路已经统一到：

- 只用正式交付 `01/02/03`
- 只做 `T4-T7`
- `Density` 为主监督
- `HasFracture` 主要保留给最终 DFN 校正

研究内容一旧链路如果继续参与，反而会引入另一套弱标签体系，和当前正式口径冲突。


### 2) 中游样本到密度体更直接

修改后将变成：

- 正式 `01+02` 样本
- 层位挂接与清洗
- demo 区块训练样本包
- 基于真实属性统计的预测密度体

这条链已经比“虚拟井复制外推 -> 再混合训练”更短，也更可解释。


### 3) 下游 DFN 校正不会被污染

当前 `03` 已明确只用于最终 DFN 校正。

修改后：

- 不再让旧的伪虚拟井弱标签干扰 DFN 前半段
- 下游仍可以直接接 `密度体 -> 初始DFN -> 03校正包`


## 7. 最终建议

当前最合理的继承策略是：

- 保留 `研究内容一` 的工程外壳
- 放弃 `研究内容一` 的虚拟井外推方法
- 以 `当前任务` 目录作为唯一正式主线

如果后续还要继续用“虚拟井”这个词，它在当前项目里应只表示：

- 来自正式 `02` 交付的井周外推结果

而不再表示：

- 研究内容一旧代码里那种“复制源井 + 距离衰减”的原型样本
